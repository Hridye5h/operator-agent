# Models, APIs, frameworks and components used

Everything third-party in this project, and what it is used for.

## Language and runtime

| | |
|---|---|
| Python | 3.14.3 |

## Models

| Model | Used for | Notes |
|---|---|---|
| `gemini-2.0-flash` (Google) | Planning only — choosing the next action from the observation buffer | Optional. Without `GEMINI_API_KEY` the system runs a deterministic planner and prints `planner=scripted` on every run. |

No model is used for extraction. Reading fields off an invoice is deterministic
parsing (`tools/files.py`), because a parser that fails loudly is preferable to a
model that quietly returns a plausible figure. See `DECISIONS.md` §4.

No model is fine-tuned, and no training data is used.

## External services

**None at runtime**, apart from the Gemini API when a key is configured.

The agent reaches nothing outside `127.0.0.1:8099` and the local filesystem. No
real company system, no third-party account, no credentials. The "internal
system" is `mockenv/internal_app`, written for this project.

**No agent framework is used.** LangGraph, LangChain, CrewAI and similar were
not used. The loop is explicit, in about 150 lines, because the verification
gate, the confidence reroute and the state binding are the interesting parts and
burying them in framework callbacks would make them harder to read, test and
defend. Reasoning in `DECISIONS.md` §8.

## Data

All documents are synthetic, generated by `mockenv/invoices/generate_invoices.py`.
Vendor names are fictional. No real invoice, company record or personal data is
present anywhere in this repository.

## AI coding tools

This project was built with AI coding assistance (Claude), which the brief
permits. The architecture, the design decisions recorded in `DECISIONS.md`, and
the defects described below were worked through directly, and I can walk through,
debug or extend any part of the system.

Defects found and fixed during development, as examples of what that work looked
like:

- A human's free-text reply to an escalation was scanned for the first number it
  contained, so "see the email from 15 March" became a payable of 15.00. This
  defeated verification, since verification compares the write against intent and
  the intent was already wrong. Replies now only resolve an ambiguity if they
  name one of the amounts in question.
- `Tool.requires_approval` was declared and advertised to the planner but never
  enforced by the loop — a safety control that did not exist.
- "Refuses to guess" was enforced only by the deterministic planner's rules. A
  planner that ignored the ambiguity got its guess written, and verification
  then passed because it compared fewer fields than were written. Both are now
  invariants of the loop.
- A failed submission stays in the history for the rest of a run, so recovery
  branches kept firing after the goal had already been met, sending the agent
  into a verify loop until the step budget was exhausted.
